# Internationalisation

English and Vietnamese, switched at runtime without a reload; every date, number, amount
and plural formatted for the reader's locale; the time policy (rule 9) verified across
time zones; and the layout prepared for a right-to-left language without shipping one.

Decisions: [ADR-0004](decisions/0004-bundled-translations.md) (translations as chunks),
[ADR-0009](decisions/0009-translated-route-titles.md) (titles),
[ADR-0032](decisions/0032-runtime-locale-formatting.md) (formatting),
[ADR-0033](decisions/0033-plurals-by-cldr-category.md) (plurals),
[ADR-0036](decisions/0036-style-rules-and-logical-properties.md) (RTL readiness).

---

## 1. The architecture

```text
core/i18n/
  languages.ts                  code → locale → direction      en → en-US, ltr; vi → vi-VN, ltr
  bundled-translation.loader.ts code → lazy JSON chunk          one import() per language
  translations/{en,vi}.json     the copy                        same keys, checked by a test
  language.service.ts           the active language, as a signal; switch; persist; follow tabs
  locale-format.ts              Intl formatters, cached per locale
  locale-pipes.ts               appInstant · appDateOnly · appNumber · appCurrency · appPlural
core/seo/document-language.ts   <html lang dir> follow the language
core/seo/translated-title.strategy.ts   the tab title follows it (ADR-0009)
```

**Three words, kept apart.** A _language_ (`vi`) keys a translation file. A _locale_
(`vi-VN`) is what `Intl` formats with - digit grouping, date order, currency position. A
_direction_ (`ltr`/`rtl`) is what the layout flips on. One file per language; the locale
and direction are data in `languages.ts`.

**Transloco** (locked, ADR-0001) holds the translations and the active language. Templates
read copy with `*transloco="let t"`; TypeScript that needs a string reads it through
`TranslocoService.translate(key, params, lang)` with the language signal, so a
`computed()` re-runs on a switch (see `customer-form.ts`).

## 2. Switching language

`LanguageService.use(code)`:

1. ignores a code the application does not ship;
2. writes it to `localStorage` (`ecm.language`);
3. **loads the chunk first**, then makes it active - the other order re-renders every
   template against a dictionary that is not there yet;
4. Transloco's `langChanges$` then updates the `active` signal; `<html lang dir>`, the
   title, every `*transloco` template and every locale pipe follow. Nothing reloads -
   `e2e/i18n.spec.ts` proves it with a `window` marker that a reload would erase.

**Starting language**: the stored choice, else runtime configuration's `defaultLanguage`,
chosen after `/config.json` has loaded (in `provideRuntimeConfig`, because initialisers
start together and a separate one would read the defaults). Awaited, so the first render
is already in the user's language.

**Server rendering**: prerendered and server-rendered HTML is always the default language.
It is shared by every visitor and must not carry one user's choice. A Vietnamese user who
loads `/login` cold sees English HTML for the moment before the application starts, then
Vietnamese - asserted in the E2E suite.

**Other tabs** follow through the `storage` event, as the theme does (docs/cross-tab.md).

**The switcher** (`layout/language-switcher.ts`) is a `choice` menu: `menuitemradio` items,
the current one checked, each name written in its own language with its own `lang`
attribute, and a trigger whose accessible name ("Language VI") contains its visible text.
It is in the header on wide screens, in the drawer on a phone, and on the sign-in page.

## 3. Formatting

Never string-built. Every value goes through `Intl`, with the active locale:

| Value                        | Template                             | English (`en-US`)   | Vietnamese (`vi-VN`) |
| ---------------------------- | ------------------------------------ | ------------------- | -------------------- |
| An instant (`updatedAt`)     | `{{ at \| appInstant: 'short' }}`    | `9/28/26, 4:56 PM`  | `16:56 28/9/26`      |
| A calendar date (`DateOnly`) | `{{ dob \| appDateOnly }}`           | `January 1, 1990`   | `1 tháng 1, 1990`    |
| A number                     | `{{ total \| appNumber }}`           | `50,000`            | `50.000`             |
| Money                        | `{{ amount \| appCurrency: 'USD' }}` | `$1,234.50`         | `1.234,50 US$`       |
| A count in a sentence        | `{{ key \| appPlural: count }}`      | `Import 1 customer` | `Nhập 1 khách hàng`  |

- **Instants** use named styles (`short`, `medium`, `time`, `timeWithSeconds`), never a
  pattern - the pattern is what differs between locales. They are shown in the viewer's
  time zone, at render time only; storage and transport stay UTC ISO-8601.
- **Money: the currency belongs to the amount.** The language decides only how it is
  written. Choosing the currency from the language would relabel dollars as dong. The
  dong has no minor unit and `Intl` knows it (`1.234.568 ₫`). The domain has no money
  field; the performance lab's totals, the rendering specimen's catalogue and the locale
  lab use it.
- **Numbers inside messages**: a parameter passed straight to `t()` is formatted with
  `appNumber` at the call site. Messages recorded far from where they are shown - a
  notification, a confirmation - carry raw numbers, and the host formats them with
  `LocaleFormat.params()`.
- **Why impure pipes**: the language is not a pipe argument, and a pure pipe is memoised
  on its arguments, so it would keep the old language. The formatters are cached per
  locale and the application is zoneless and OnPush, so running them on each change
  detection of their view costs nothing measurable. (ADR-0032.)

## 4. Plurals

One key per CLDR plural category, chosen by `Intl.PluralRules` (ADR-0033):

```json
// en.json
"confirm": { "one": "Import {{count}} customer", "other": "Import {{count}} customers" }
// vi.json - Vietnamese does not inflect for number
"confirm": { "other": "Nhập {{count}} khách hàng" }
```

`appPlural` picks `<key>.<category>` for the count, falls back to `other`, and passes
`count` already formatted. One count per string: "2 customers imported, 1 row skipped" is
two strings, each agreeing with its own number. Phase 6 found and fixed "1 were changed
by someone else", "Clicked 1 times" and "1 rows skipped" this way.

## 5. The time policy, verified

Rule 9: instants are UTC; `dateOfBirth` is a calendar date that must never shift.
`core/time/instant.ts` encodes it; Phase 6 verifies it where it can actually break - in a
browser, in time zones on both sides of the date line:

- `e2e/i18n.spec.ts` opens one customer in **Pago Pago (UTC−11), Los Angeles, Ho Chi Minh
  City and Kiritimati (UTC+14)**. The date of birth reads identically in all four; the
  `updatedAt` instant does not (the control that proves the zones really differed).
- The same suite edits and saves a customer from Pago Pago and reads it back from the API:
  `dateOfBirth` is unchanged, and the date field showed the stored date, not the previous
  evening.
- The **locale lab** (`/technical-labs/locale`) shows the bug and the fix side by side:
  `new Date('1990-01-01')` reads _December 31, 1989_ west of Greenwich; `formatDateOnly`
  reads _January 1, 1990_ everywhere.

## 6. Right-to-left, prepared

Not implemented - no RTL language ships - but a matter of adding one:

- `languages.ts` carries `direction`; `<html dir>` is written from it.
- Every stylesheet uses **logical properties** (`margin-inline-start`, `inset-inline-end`,
  `text-align: start`), and `npm run lint` fails on a physical one (`lint/styles.ts`).
- CDK overlays and menus read `dir` and mirror themselves.

What would remain for Arabic or Hebrew: a translation file; mirroring the few CSS-drawn
directional glyphs (pagination chevrons, the filter disclosure arrow, the breadcrumb
separator); and checking the icon rail.

## 7. Adding a language

1. `translations/<code>.json` with every key of `en.json`. Plural entries use only the
   categories that language has (`new Intl.PluralRules(locale).resolvedOptions()`).
2. One entry in `TRANSLATION_CHUNKS` (`bundled-translation.loader.ts`).
3. One entry in `SUPPORTED_LANGUAGES` (`languages.ts`): code, locale, direction.
4. Its name, in itself, under `language.names` in **every** file.

`translations.spec.ts` fails if the files' keys, parameters or plural shapes disagree, or
if the loader and the language list do.

## 8. Known limits

| Limit                                                                          | Why                                                                                      |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `<input type="date">` shows the browser's date format, not the page's language | No web API controls it; the value is ISO in every locale                                 |
| The browser's `beforeunload` dialog is in the browser's language               | Browsers ignore custom text there (anti-phishing); the in-app leave dialog is translated |
| Prerendered pages are English until the application starts                     | Shared HTML cannot carry one user's language (section 2)                                 |
| Translations change only with a deployment                                     | ADR-0004: they are bundled chunks                                                        |
| The i18n lint rule's `ignoreAttributes` list is at 18 entries                  | Debt row 16: past ~20, a custom rule is cheaper                                          |
| `en` formats as `en-US`                                                        | One entry in `languages.ts` changes it; no deployment has asked                          |
